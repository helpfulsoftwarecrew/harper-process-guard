# AGENTS.md

For whoever changes this repository. `README.md` is for whoever uses it.

## Rules that are load-bearing

Each of these was paid for once. `README.md` explains what they protect.

- The lock is decided inside a gate one thread holds at a time and is replaced only by `rename`. Check-then-delete let the second thread's delete take the winner's file: 23 of 300 eight-thread races. The race suite runs 60 rounds on Windows, where every identification is a PowerShell start, which still meets that rate several times over.
- A claim and a gate are given up by their own age, never by how long a waiter has waited. An unfinished claim whose claimant lives is taken over once it is older than the waiter's budget, and a live holder's gate once it is older than the longest hold (`gateWaitMs`); a dead holder's gate goes at once. Judged by the waiter's own wait, a caller at its deadline took over a claim another had made 2 ms before, and two threads without keepers each started a copy, 4 of 5 runs; a writer broke a gate another holder had taken half a second before. A holder removes the gate on its way out only while the gate still carries its own mark: removed whoever held it, a holder whose gate had been broken removed the breaker's, and a third thread got in beside the breaker, 3 of 3 runs.
- Nothing is signalled without a positive identification, and "cannot tell" never reads as "not ours", for the lock too: an `unknown` verdict waits out the claim rather than taking the lock.
- The kill path is opt-in and off by default: `stopOrphans`, and launching a reaper at all. A signal sent on a wrong identification cannot be taken back.
- Identity is the command line, never the executable, which resolves to the interpreter for every node script. A pid whose parent is the keeper its lock names is identified by that parent too: a keeper starts nothing but its process and, on macOS, the `ps` reads it waits on, while a binary that execs changes its command line under the same pid. Without that, one `guard()` call on a script that ran `exec sleep` had two copies running 14 s after one SIGKILL, 3 of 3 runs. The parent vouches only once it identifies as that keeper by the `keeperArgv` the lock records: on the parent pid alone, a stale lock whose keeper and process pids had passed to a shell and its child had the claim join that child, and both a new version's claim and the reaper SIGTERM it. Pid 1 vouches for nothing, since it adopts every orphan. A pid whose start time is the one its keeper recorded at commit is that process whatever it runs, since an exec keeps the start time and a process that reuses the pid has its own; that is what identifies it once its keeper is killed. A readable start time that is not the recorded one is another process, whatever it runs: read through to the command line, a process started again under the same command and a pid the lock once named was taken for the locked one, and the reaper sent it SIGTERM. Without it, a script that execs was taken for a stranger after a SIGKILL to its keeper, and the next claim started a second copy, 3 of 3 runs. On macOS `ps` runs with the host's `LANG` and every `LC_*` removed, `LC_CTYPE=UTF-8` and `TZ=UTC`, since the keeper runs in the process's environment and the thread in the host's. Under `LC_ALL=C` it escaped every non-ASCII byte of a command line, so a `pidDir` holding one had each `guard()` call start another reaper; and one invalid locale variable, `LANG=garbage` or `LC_MESSAGES=garbage`, leaves it in C whatever else is set. On Linux the ticks from boot carry the boot's id, since a lock outlives a reboot and the ticks repeat.
- Pid 1 is a process. Inside a container it is usually the host.
- The reaper removes a lock before signalling what it names, and is spawned by path, never imported. Because it removes the lock, a lock that is gone no longer proves a deliberate stop: a joiner whose process died and whose lock is gone restarts the process when the host that held the lock is dead, and leaves the death to that host while it runs.
- A reaper removes its own lock on the way out only while the lock names it. A host whose reaper runs another command line, as one does after a restart, takes the lock for its own reaper and leaves the old one running, and the old one leaving removed that lock: in the e2e test of two hosts that joined a third, the reaper lock was gone once the killed host's reaper finished, 3 of 3 runs, while both survivors' reapers ran. A stop signal leaves the lock alone, naming a pid that is gone once the reaper exits, which the next claim reclaims: releasing it through the gate kept a stopped reaper alive 7 s behind a gate another held, and its gate files landed in a pid directory the stopper was removing, which failed the plugin's partial-logger teardown 19 of 20 runs against 0 of 20 with the lock left alone. A lock whose directory has gone is `gone`, and logs nothing.
- The reaper reads each lock inside its gate as it removes it, and decides on the pid it names then. A keeper restarts a crash after its host is gone, so a pid the reaper listed earlier can be dead by its turn: deciding on that one left the keeper's restart running with no lock, and the next host started a second copy, 3 of 3 runs.
- A pid the caller's `spawn` hands back is the process only when Node created it for that call (`spawnfile` is set); a wrapper's pid is identified first, and a stranger fails the attempt. Harper's own spawn returns a stale pid file's pid whenever `kill(pid, 0)` answers, and after a restart that is a thread of Harper itself. A pid the platform cannot describe is taken on trust, which on Windows is a CIM lookup that did not answer; that gap is known. `clearStaleHostPidFiles` spares a host pid file naming a keeper only when that keeper carries the name's own lock: sparing any keeper, a one-hour soak on Harper 5.2.9 had an agent's keeper take the pid Harper recorded for the reaper, and for the rest of the hour every relaunch was handed that keeper back instead of a reaper.
- `spawn` comes from the caller. That is what makes the guard testable with a fake and usable by a host that constrains `child_process`.
- On POSIX the process's parent is a keeper, never a worker thread: Node delivers an exit and reaps a child only on the event loop that spawned it, so once a host ends that thread a deliberate stop reads as a crash and each death leaves a zombie. The launcher exits at once so init adopts the keeper; spawned without one, the keeper itself is left a zombie of the host. A worker ended within about 30 ms of calling `guard()` can still leave the launcher a zombie, 12 of 12 runs at 5 to 30 ms and none from 35 ms: nothing reaps a pid that a thread now gone spawned, so the window only shrinks.
- A keeper writes its record inside the gate before it removes the lock, and a thread that rejoins after a `restarting` record only adopts, never claims. With the rejoin going back through the claim, the cap test started the process past the cap in 2 of 3 runs: the keeper had already given up and released. The rejoin has no deadline either: it hands the death to the lock only once the lock has changed hands or its keeper is gone, since a live keeper always commits or records. Each pass looks at the keeper before it reads the lock and the record. Looked at after them, a keeper that committed a restart, saw it stopped, recorded that and exited in between was taken for gone without a word, and a joiner whose lock host was dead started the process again, in 10 of 10 runs of the test that holds that gap open.
- A start answers any record under its own token before it concludes that its claim was taken: a process that exits between two of its looks leaves the lock gone and the record behind, and reading the lock alone reported `/usr/bin/true` as never started in 5 of 5 runs.
- A failed start's record says whether its keeper removed the lock, and the thread gives its claim back only when the keeper did not. The lock the thread read before the record can predate that removal, and releasing it again logged a false error in 1 of 300 starts.
- A thread that stops waiting on its keeper gives its claim back inside the gate only while the lock names no pid, and joins a pid the keeper has committed. Released on its token alone, a lock committed just past the thread's 16 s deadline was removed under a running process, and the next claim started a second copy, 3 of 3 runs.
- A stdout or stderr the caller pipes is relayed by the keeper and never handed to the process. The pipe's reader is the thread that spawned the keeper: handed the pipe, a process died on its first write once that thread ended, and the keeper restarted it into the same pipe until the cap, `died 6 times (signal SIGPIPE)`. On its way out the keeper waits for relayed output to drain; without the wait, a reader that paused every 64 KiB lost 196608 of 1048576 bytes on each pipe, 5 of 5 runs. The cost is that a SIGKILL to the keeper ends a piped process on its next write, 3 of 3 runs. A piped stdin is the keeper's own, held open and never written: the thread's end closes as the launcher exits, and handed that, a process watching for end-of-file had read it 300 ms after its start in 3 of 3 runs, where it had read none while its thread lived.
- A thread sets how a process ended before it sets `exited`, so under a keeper it reads the record first. Set the other way, a thread that saw the death through its poll showed `exited` with no code until the record landed, which failed the macOS CI leg once and 10 of 10 runs with the keeper's record write held 30 ms, and left a status endpoint no code to report.
- A death with no record whose keeper is gone is not restarted; the next `guard()` call starts the process. Nothing can read an orphan's exit status, so the death may be a stop: answered from the lock, a SIGTERM after a SIGKILL to the keeper was restarted by a joiner in 3 of 3 runs.
- A double stands in for an external boundary only. A test that mocks part of `src/` and asserts how the mock was called is not coverage; it has to assert what a real pid, lock or process did.

A green suite is not a review. A change to `lock.js`, `supervise.js` or `reaper.js` gets an adversarial read, and every new or changed test is mutation-checked by hand: revert the production change, see it go red, restore it.

## Layout

Eleven files under `src/`, ESM with `// @ts-check` and JSDoc, nothing built. Five are the lock and what it
arbitrates; the rest are what every consumer of it turned out to need before it could supervise anything at
all, each written inside a consumer first and moved here once it proved to be about supervision rather than
about what the consumer runs.

- `identity.js`: one `inspect()` per pid answering liveness, command line, parent and start time together, one branch per platform. The Windows branch costs a PowerShell start, so `isAlive` never asks for the command line. A lone start took about 400 ms against 3.5 ms for `ps`, and eight at once took 2.9 to 3.6 s apiece on a 2-vCPU `windows-latest` runner, which is what `CIM_TIMEOUT_MS` is sized for.
- `lock.js`: the gate, `adjudicate()` (reads, changes nothing), and the writes: `claimLock`, `commitLock`, `releaseLock`, a waiting thread's `releaseUnstarted`, and the reaper's `removeLock` and `releaseOwnLock`. `safeLockWrite` turns a rejected or superseded write into a message.
- `supervise.js`: start or join, watch, and answer a death from its keeper's record; without one, by going back through the lock, or not at all once the keeper is gone as well.
- `reaper.js`: the detached script. SIGTERM or SIGINT to it logs one line and exits, leaving its own lock to the next claim.
- `keeper.js`: the script between a thread and its process on POSIX, spawned by path through its own `--launch` mode. It commits each pid and its start time under the claim's token, restarts a crash while the lock carries that token, and writes every death to `<name>.pid.exit`, which is how a thread that did not spawn the process learns how it ended. It writes nothing of its own to stdio, since a pipe to a thread that is gone would end it on the first write, and where the caller pipes stdio it relays the process's output and holds its stdin.
- `index.js`: `guard()`, `fingerprint()`, `supervisorFor()` and the two supervisors behind it, plus the re-exports that are the public surface. The reaper is launched before any `verify`: a probe can wait 30 seconds, and a host killed inside that window must not leave its processes behind.
- `exit.js`: one reading per way a process can fail to run or stop running, from `errnoCode` up to `describeExit`, which decides whether a restart would fight an operator. `supervise.js` and a consumer's status endpoint both read it, so they cannot disagree about the same signal.
- `verdict.js`: when a proof stops describing the process that is running. The supervisor rewrites `pid` on the state object a status endpoint is holding, so a verdict taken at boot outlives what it proved. A death nothing here replaces drops the verdict on that thread, and one found exited is never retaken: after a stop under a keeper, both a starting and a joining thread read as verified. `retakeVerdict` hands the proof a `reason`, because a boot poll can wait 30 seconds for a process just spawned while a retake on the read path holds a status request open.
- `node.js`: the node rather than the thread, in two halves. `claimSingleton` picks one writer for periodic work and `sharedMarks` is a value every thread can read; `nodeProcess`, `currentReaper` and `keepReaperAlive` answer what the node has when a thread's own memory says otherwise.
- `host.js`: the Harper boundary, which is four things a consumer wrote for itself first. `normaliseLog` fills a partial logger, `watchForNeverCalled` catches a host that imports a component and never calls its plugin, `hostRoot` and `resolvePort` read what Harper exposes to nobody, and `writeFiles` is temp-and-rename because every worker thread writes the same files.
- `probe.js`: polling an endpoint or a unix socket until something answers, with a doubling backoff and a `giveUp` for a process that has died. `untraceWith` is how a consumer inside a traced application keeps its own probes out of the host's APM.

Two names were one letter apart and one file had no subject: `supervise.js` supervises a process, and
`supervision.js` was fifteen exports across three ideas. It is gone. Its three parts went to the file that
already owned each idea, which is why `index.js` holds the two supervisors: `bundledSupervisor` is a caller
of `guard()`, and they belong on the same page.

`test/unit/package.test.js` pins the public surface. A name joins it on the test every file above passed: a
consumer needed it, and it is about supervising processes on a Harper node rather than about what those
processes do.

Timings a test needs to wind down live on the context (`tuning`) or in `ReaperOptions`.

## Commands

`npm test` is `node --test`, no build. `npm run typecheck` is `tsc --noEmit`. `test.yml` runs `format:check`, `lint`, `typecheck` and `test` on Linux, macOS and Windows against Node 22 and 24, and `test/unit/package.test.js` reads that workflow so the matrix and the gate cannot drift from what is written here.

Fixtures must not set `process.title`: the command line is the only identity there is. A fixture that has to survive a signal announces itself on stdout first, because it is in the process table before its handler exists.

## Publishing

A hand-pushed `v*` tag runs `publish.yml`: the full matrix, a refusal while `package.json` is private or the tag disagrees with it, then `npm publish` under `next` for a prerelease and `latest` for a stable version. `NPM_TOKEN` is a repository secret: it creates a name on its first publish and writes dist-tags; once the trusted publisher on npmjs.com names this repository and `publish.yml`, the OIDC exchange runs first and provenance comes from it. Provenance is requested explicitly (`NPM_CONFIG_PROVENANCE`), since a publish the token authenticates does not attach it on its own. The tarball is `src/` as written.

A version the registry already holds is not published again, and `latest` is left alone when it already names the version or a newer stable one. The publish check is `npm view name@version`, which reads the packument, and the packument can trail a publish by more than 20 minutes: a re-run of a job that failed after its publish can still fail on the registry's refusal inside that window, and a re-run after it finishes the job.

## Voice

Comments, commit messages and docs: no em dashes and no hyphen standing in for one, no triads, lead with the claim, stop when it lands. These rules are the whole of the voice; nothing here names a style guide or the tool that wrote a change.
